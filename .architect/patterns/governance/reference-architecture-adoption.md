# Reference Architecture Adoption

## Purpose

Apply an existing reference architecture deliberately so projects can reuse
approved building blocks and constraints without treating the reference model as
an unquestioned template.

## When To Use

- a project should align to an established reference architecture
- reuse, standardization, or governance consistency matters materially
- the team needs clarity on what must be adopted versus what may be adapted

## When Not To Use

- no meaningful reference architecture exists
- forcing adoption would hide real project-specific constraints

## Assumptions

- the reference architecture is current enough to be useful
- adoption and deviation criteria can be stated
- project teams can link local decisions back to the reference model

## Key Components

- applicable reference architecture scope
- required versus optional elements
- explicit adaptation or exception path
- traceability from project artifacts to the reference model

## Benefits

- improves reuse and consistency
- reduces repeated architecture invention
- supports clearer governance conversations

## Tradeoffs

- may constrain local optimization
- requires reference models to stay relevant
- can become cargo-cult adoption if rationale is weak

## Common Risks

- adopting a stale reference architecture blindly
- unclear boundaries between required adoption and local choice
- deviations not being documented explicitly
