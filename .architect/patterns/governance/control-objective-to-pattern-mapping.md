# Control Objective To Pattern Mapping

## Purpose

Map governance, risk, or compliance control objectives to reusable architecture
patterns so control intent can be implemented more consistently across
solutions.

## When To Use

- the same control objectives recur across many projects
- architecture review needs a clearer path from control intent to solution shape
- teams need practical design guidance instead of abstract control language

## When Not To Use

- control objectives are too immature or unstable to map meaningfully
- the need is one-off compliance interpretation rather than repeatable design

## Assumptions

- control objectives can be defined explicitly
- reusable patterns exist or can be curated against those objectives
- governance teams accept that patterns support, but do not replace, assurance

## Key Components

- control objective catalog
- mapped reference patterns
- usage guidance and exceptions
- review and evidence expectations

## Benefits

- improves consistency between architecture and compliance intent
- helps teams move from policy language to design choices faster
- supports more repeatable review outcomes

## Tradeoffs

- requires curation and maintenance as controls or patterns evolve
- can oversimplify nuanced control interpretation
- needs care to avoid treating a pattern as automatic proof of compliance

## Common Risks

- stale mappings after standards or controls change
- false confidence when a pattern is applied poorly
- governance teams and delivery teams interpreting mappings differently
