# C4 Bridge

## Purpose

Help teams who use the [C4 model](https://c4model.com/) for visual
architecture communication adopt Open Architect's structured backbone
without giving up their preferred diagramming convention.

## When To Use This Bridge

- the team already produces C4 diagrams for stakeholders
- the team wants Open Architect's structured artifacts as the source of
  truth but C4 as the visual face
- diagrams are a primary communication artifact, not just an internal aid

## Concept Mapping

| C4 concept | Open Architect equivalent | Notes |
|---|---|---|
| Person | `stakeholder` (with concerns) | C4 "Person" is a user or actor; Open Architect's stakeholder also carries concerns and influence |
| Software System (in scope) | `solution` or `application` | Use `solution` when modeling a bounded design; use `application` when modeling a system in the existing estate |
| Software System (out of scope) | `application` (with metadata flagging it as external) | External systems still belong in the metamodel so relationships can be drawn |
| Container | `application-service` or `technology-component` | C4 "Container" is ambiguous — for a deployable unit/process use `application-service`; for the platform under it (DB, queue, runtime) use `technology-component` |
| Component | `application-service` (finer-grained) | Most projects don't model below `application-service`; only go deeper when a real review needs it |
| Code | not modeled | Code lives in repositories, not in the architecture metamodel |
| Relationship (uses, sends to, etc.) | typed `relationships` block | Open Architect uses explicit relationship types like `realizes-capability`, `depends-on`, `exposes-interface` |
| System Context diagram | a view (markdown / Mermaid / draw.io) under `workspace/<project>/views/` | The diagram references stakeholders + applications + organizations; the underlying YAML is the truth |
| Container diagram | a view referencing applications, application-services, interfaces | Pull the elements from existing artifacts; do not invent diagram-only entities |
| Component diagram | a view referencing application-services at finer granularity | Same rule — diagram is presentation, not separate truth |
| Code / class diagram | out of scope | Belongs in code-level documentation |
| Deployment diagram | a view referencing `environment` and `technology-component` | Open Architect has explicit `environment` artifacts for this purpose |

## What Doesn't Map Cleanly

- **C4 "Container"** is intentionally ambiguous — sometimes a process, sometimes a database, sometimes a queue. Open Architect splits these into `application-service` (logical service) and `technology-component` (runtime / platform). Pick consistently per project, document the choice.
- **C4 "Software System"** is also intentionally ambiguous — sometimes a black-box product, sometimes a bounded scope of the design. Open Architect distinguishes `solution` (the bounded design you are authoring) from `application` (a system that exists in the estate).
- **C4's diagram hierarchy** (Context → Container → Component → Code) is finer than Open Architect's view types. Most projects use Context and Container; Component diagrams are rare in Open Architect projects unless a review specifically needs them.
- **C4 does not model**: capabilities, principles, standards, decisions, transitions, governance, risk, compliance. Use Open Architect templates for these.

## Recommended Usage Pattern

1. Use Open Architect templates (`stakeholder`, `application`, `application-service`, `interface`, `data-object`, `technology-component`, `environment`) as the structured backbone.
2. Use [`diagram-author`](../../skills/diagram-author.md) to produce C4-style views.
3. Store the views under `workspace/<project>/views/`.
4. Every C4 diagram element should resolve to an existing artifact ID. No diagram-only entities.
5. Treat C4 as **presentation**, not as a parallel truth.

## Common Confusions

- "C4 has no concept of a capability." Capabilities (and the rest of business architecture) live in Open Architect, not in C4. Use both.
- "C4 has no decision record." Use `decision` artifacts in Open Architect for decision records (ADR-style); C4 carries no decision content.
- "C4 lets us name a database as a Container; should that be an `application-service` or a `technology-component`?" In Open Architect terms, the database is a `technology-component`. The application's logical access to it is an `application-service`. The C4 Container in the diagram references the `technology-component`.
- "Should the C4 Person be a `stakeholder` or an `organization`?" If it's an individual or a role with concerns, it's a `stakeholder`. If it's a team or function that owns something, that's `organization`. C4's Person usually maps to stakeholder.
