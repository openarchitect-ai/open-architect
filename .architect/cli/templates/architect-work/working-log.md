# Working Log

Chronological, plain-language record of what happened on this project,
newest entry on top.

The four topical files organize by category (questions, answers,
evidence, tasks). This file organizes by time so the project's story
can be read linearly.

Add an entry when a skill runs, a scope or playbook change lands, a
sponsor or stakeholder decision is confirmed, **a project stage opens
or closes**, or anything else worth remembering. Skip routine edits —
git history already captures those.

Each entry should read clearly to someone joining the project cold.
Plain language, not jargon.

For stage transitions, use a title that names the move clearly so the
audit trail is scannable:

```
## YYYY-MM-DD — Stage transition: <from-stage> → <to-stage>
```

Examples: *"Stage transition: Frame → Baseline"*,
*"Stage transition: Solution Direction → architecture-review"*. Under
the entry, capture what triggered the transition (sponsor sign-off,
gate passed, evidence landed) so a future reader can reconstruct the
project's stage history from working-log alone.
